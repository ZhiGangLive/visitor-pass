**正文**

```

思路和市面上的反着来：不是访客申请、员工审批，而是员工发邀请、访客接受。
邀请卡就是一张 PNG，微信直接转发，访客不用装任何东西。

技术上有意思的几点：

1. 零 npm 依赖。只用 Node 内置的 http / fs / crypto / path / os / url。
   二维码用的是内置的 qrcode.js（MIT），没有构建步骤。

3. 断网可用。这是被真实场景逼出来的：有些楼不许上云，有些厂房网络本来就不稳。

4. 核验判定顺序是写死的，不可配置：限流 → 存在性 → 撤销 → 时间窗 → 重复扫描 → 名额 → 复入。

5. 门岗端的交互只做了一件事：结果用底部浮卡，不遮挡输入框。
   高峰期保安一秒要扫三个人，任何「先关掉弹窗」的设计都是添堵。

- 没接闸机/人脸，纯「人看屏幕 + 系统判定」
- 单进程，设计上限是一栋楼、日均几百访客

地址：https://github.com/ZhiGangLive/visitor-pass

**正文**

```markdown
我数了一下，这套系统 6300 行代码，零个 npm 依赖，没有数据库，没有构建步骤。

它能做的事不少：发邀请、生成四种卡面、一键复制到微信、门岗扫码、自动台账、
多级部门、16 项权限矩阵、操作审计、CSV 导出。

但它砍掉的东西更多：门禁硬件、人脸识别、访客小程序、云端多租户、SQLite、Docker、微服务。

每砍一个，我都问自己同一个问题：**加了这个，一个物业经理还能当天拍板吗？**

## 一、起因：访客系统默认你在防人

你去任何一家公司，流程几乎都一样：访客填表申请 → 员工点通过 → 保安盘问 → 放行。

这条链路里，每个人都在防着对方。访客像来求人办事的，保安像在查户口的，
邀请人像在给自己找麻烦。

更关键的是权力方向错了：**发起权在访客手上，判断权在保安手上，唯一该负责的人（邀请人）反而不在场。**

所以我把它倒过来：员工发起邀请，访客接受。填四个字段，生成一张卡，微信发过去。
到门口扫码，2 秒放行，台账自动生成。

这不是文案层面的差别，它改的是三件事：

- 发起权回到主人手里，信息一次填对
- 责任落到具体的人身上（服务端强制 `inviterId` = 当前会话用户，前端传什么都不作数）
- 门岗从「判断者」变成「核对者」，判断被前置到邀请那一刻

## 二、为什么是零依赖，而不是「最佳实践」

零依赖不是一个技术炫技，它是部署成本问题。

一旦引入 Express + SQLite + 某个 ORM，客户那边就要装 Node、建目录、配服务、
处理版本冲突。而真实场景是：一栋老写字楼，预算三千，没有 IT，只有一台旧电脑和一个保安。

零依赖之后，部署变成三条命令：

```bash
git clone https://github.com/ZhiGangLive/visitor-pass.git
cd visitor-pass
node server.js
```

Windows 上更简单，双击 `start.bat`。没有 `npm install`，没有编译，没有 Docker。

代价也很清楚：路由要自己写，模板字符串拼 HTML，所有工具都得手搓。
589 行的 `server.js` 就是全部路由。

## 三、三个真正难做的细节

### 1. 原子写：断电不能写出半个文件

访客台账是行政和安监都要查的东西。文件型存储最怕的是写到一半断电。

```js
// 先写 .tmp，再原子改名
fs.writeFileSync(TMP_FILE, JSON.stringify(db));
fs.renameSync(TMP_FILE, DB_FILE);
```

再叠三层保护：每天第一次写入自动备份（保留 7 天）、解析失败把坏文件改名隔离、
起空库保证服务能启动。

### 2. 核验判定顺序：写死，不给配置

```
1. 是否命中限流        → 尝试过于频繁
2. 凭证是否存在        → 无效凭证
3. 是否已撤销          → 邀请已撤销
4. 是否在时间窗内      → 尚未生效 / 已过期
5. 同设备 60 秒内重复扫 → 放行，不扣人次
6. 名额未满            → 放行，扣 1 人次
7. 名额已满且允许复入   → 放行，不扣人次；否则名额已用尽
```

很多人第一反应是「做成可配置的」。我试过，然后删了。
可配置的判定顺序意味着运维可以在凌晨三点改坏一条规则，
而门岗第二天早上会用它放人进来。

### 3. 门岗端：只允许有一个输入框

保安的真实状态是：一手拿扫码枪，一手拿对讲机，后面排着三个人。

所以门岗页面只有三样东西：一个输入框、一句提示、一张当日台账。
结果用底部浮动卡（通过 2.4 秒自动收起，拒绝停留 6 秒），**不遮挡输入框**。
任何需要「先关掉弹窗才能继续扫」的设计，在高峰期都是灾难。

## 四、一张通行证，为什么要做四种样式

因为它不是通行证，它接近一张请柬。

四种卡面（票券 / 极简白 / 墨金 / 青玉），同一套数据、同一尺寸 1080×1350。
人收到请柬和被发一张通行证，感受是不同的——这是「尊重」在像素上的具体形状。

技术上没什么难度，就是 Canvas 画图 + 四种排版函数。但它决定了这套系统
像不像一个「请人来」的产品。

## 五、已知限制

写在 README 里，也写在这里：

- 4 位邀请码理论可枚举。已加失败限流，但真正的强校验是二维码里的 `SL` + 10 位凭证号
- 复入放行默认开启。系统拿不到身份信息，区分不了「同一个人出去吃饭回来」和「另一个人拿转发图来」
- 局域网 http 下剪贴板写入被浏览器拦，有右键复制和下载 PNG 兜底
- 没接闸机、人脸、身份证读卡器
- 单进程，没有集群和分布式锁，设计上限是一栋楼

## 六、为什么选 AGPL 而不是 MIT

MIT 更流行，但我不能选它。

这套系统的价值主张是「数据在你自己手里」。如果允许任何人拿去做闭源 SaaS，
这个前提就没了——用户的数据又回到了别人的服务器上。

AGPL 保证改动必须回流。同时留了商业授权的口子，给需要闭源集成和 OEM 的场景。

这句话可以是夸奖，也可以是别的意思。取决于你是那个访客，还是那个邀请他的人。

## 一、三种人，各付了一笔隐性成本

大部分访客系统默认「审批」：访客申请、员工点通过、保安核验放行。

这条链路看起来严谨，实际上把成本转嫁给了三个不发声的人。

**访客付出的，是尊严。**
他要填身份证号、手机号、来访事由，等一个不确定的「通过」，
然后在门口被问「你找谁」「预约了吗」「让他下来接你」。
他是来谈合作的，此刻却像来办证的。

**保安付出的，是敌意。**
系统把判断权交给了他，却没给他足够的信息。他只能靠盘问来补足，
于是每一次放行都变成一次小型审讯。久了，他会习惯用怀疑的眼光看所有人。
这不是他的问题，是设计的问题。

**邀请人付出的，是责任的模糊。**
出了事，系统里查不到「谁请的」，只能查到「谁放的」。

三笔成本，没有一笔写进采购清单。

## 二、把动词换一下

我们做了一套开源系统，只改了一个地方：不是访客申请，是员工邀请。

- 员工填四个字段，生成一张卡；
- 微信转发过去，访客不注册、不下载、不填表；
- 到门口出示，保安扫码，2 秒放行；
- 台账自动生成，谁进来过一查就有。

客户、供应商、面试者、竞争对手——只要是被邀请的，就按客人对待。

这不是一句文案。它是权限设计：**发起邀请的人，固定是当前登录账号本人，
服务端不接受前端指定他人。** 谁请的客，责任就是谁的。

## 三、理念要落在工程上，否则只是文案

「尊重」这种词，写在官网首页毫无成本。它只有在代码里才有重量。

**访客零安装。** 邀请就是一张 1080×1350 的 PNG，微信能发、能存、能打印。
所有成本留在主人这边，不转嫁给客人。

**门岗只有一个输入框。** 扫码枪和手输共用一个框，回车即核验。
结果是底部浮卡，不遮挡输入框——因为保安高峰期一秒要扫三个人。

**卡面上是一个人的名字，不是一张表。**
四种卡面：票券、极简白、墨金、青玉。它更接近一张请柬，而不是一张通行证。

**数据留在自己手里。** 一个 JSON 文件，拷走就是全部。不上云、不锁定、不做多租户。

## 四、邀请制不等于没有安全

这点必须说清楚。

时间窗、名额、撤销、限流、去重、留痕、强凭证，一条都没少。
区别只在于：**它防的是「无效凭证」，不是「可疑的人」。**

前者是事实判断，保安做得又快又准；后者是人身判断，只能靠猜，
而猜错的代价由公司承担。

## 五、克制也是尊重

这套系统不做门禁硬件、不做人脸识别、不做访客 App、不做云端多租户。

不是因为做不到，是因为每加一样，部署成本、决策链条、失败概率都上升一档。

一家物业公司想给老写字楼装访客系统，预算三千，没有 IT，只有一台旧电脑和一个保安。
如果产品要求闸机、要求人脸、要求上云，它就永远用不上，只能继续用纸质登记本——
那本子上的每一页，都写着上一个访客的身份证号。

**能被一个物业经理当天决定、当天上线的系统，
比一个功能齐全但要走三个月采购的系统，更有价值。**
