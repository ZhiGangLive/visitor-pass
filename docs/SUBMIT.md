## 渠道 A：腾讯云开发者社区（推荐，当天可发）

### 标题

```
把一个想法做成能跑的开源项目：访客系统的「邀请制」改造
```

### 正文（可直接粘贴，约 1200 字）

公司访客登记一直用纸质本。行政嫌乱，保安嫌烦，访客嫌像审问。

更别扭的是流程本身：访客填表申请、员工点通过、保安在门口盘问。
发起权在访客手上，判断权在保安手上，唯一该负责的人——邀请人——反而不在场。

我们把这套流程倒过来做，最后开源了。这篇文章记录两件事：
为什么改，以及怎么在 WorkBuddy 里把「一个想法」做成「一个能交付的开源项目」。

## 一、先承认一件事：想法不值钱

「邀请制访客」不是新点子。飞书的访客大师、钉钉的智能来访、各家 SaaS 都是这个路子。
真正稀缺的不是点子，是把它变成能跑、能装、能交付的东西。

所以我们给自己定了四条硬约束，每一条都在砍需求：

1. **零 npm 依赖**，只用 Node 内置模块。客户那边不需要 `npm install`。
2. **零数据库**，全部数据是一个 JSON 文件，拷走就是全部。
3. **零联网要求**，断网也能发邀请、核验、查台账。
4. **访客零安装**，邀请就是一张能发微信的 PNG。

每砍一个功能，我都问同一句话：加了这个，一个物业经理还能当天拍板吗？

## 二、用 WorkBuddy 做了什么

代码是前几个月陆续写的。真正把它变成「一个项目」的，是最近这一轮在 WorkBuddy 里做的事：

**1. 把 README 从说明书改成立场文件**

原来的 README 是功能清单。改写时先讲「为什么是邀请而不是审批」，
再讲功能和接口。开源项目最缺的不是文档，是「为什么要有这个东西」。

**2. 用浏览器自动化截了 9 张界面图**

让 WorkBuddy 起本地服务、注入登录态、按路由逐页截图，
输出 1440×900 @2x。省掉了手动截图再裁剪的两小时。

**3. 录了一支 57 秒的演示视频**

Playwright 录真实操作（填表单 → 生成卡面 → 复制图片 → 门岗扫码 → 台账新增），
再用 ffmpeg 拼接文字卡、压字幕。横版 1920×1080 和竖版 1080×1920 各一版。
没有配音，字幕烧录，方便二次剪辑加 BGM。

**4. 补了冒烟测试和 CI**

零依赖的端到端脚本，临时目录起服务，跑 21 项断言：
登录、建邀请、邀请人防伪造、首次入场、同设备去重、无效凭证、台账、CSV BOM、越权拦截。
GitHub Actions 上跑 Node 16/18/20/22 四档，外加「依赖数必须为 0」的策略检查。

**5. 把发布物料一次做齐**

V2EX、掘金、知乎、公众号、小红书、B 站六套文案，加上社交封面和视频封面。
这些不是「顺便写写」，它们决定了项目有没有人点进来。

## 三、三个值得抄的工程细节

**原子写。** 访客台账是行政和安监都要查的东西，最怕写到一半断电。

```js
fs.writeFileSync(TMP_FILE, JSON.stringify(db));
fs.renameSync(TMP_FILE, DB_FILE);
```

再叠三层：每日自动备份保留 7 天、解析失败隔离坏文件、起空库保证服务能启动。

**核验判定顺序写死，不给配置。**

```
限流 → 存在性 → 撤销 → 时间窗 → 重复扫描 → 名额 → 复入
```

很多人第一反应是做成可配置。我试过，然后删了。
可配置意味着运维能在凌晨三点改坏一条规则，而门岗第二天早上会用它放人进来。

**门岗端只允许有一个输入框。**
保安的真实状态是一手扫码枪、一手对讲机、后面排三个人。
所以结果是底部浮卡（通过 2.4 秒收起），**不遮挡输入框**。
任何需要「先关掉弹窗才能继续扫」的设计，在高峰期都是灾难。

## 四、结果

- 仓库：github.com/bulusiLive/visitor-pass（AGPL-3.0）
- 6300 行，零依赖，Node 16+ 双击即跑
- CI 全绿，21 项冒烟断言
- 演示视频 57 秒，横竖两版

## 五、四条可复用的方法

1. **先定「不做什么」**，再定做什么。约束比功能更能定义产品。
2. **把理念写进代码**，否则它只是文案。比如「邀请人不可代发」是服务端强制，不是界面提示。
3. **发布物料和代码同等重要**。没人会读一个没有截图、没有视频、没有一句话简介的仓库。
4. **诚实写限制**。README 里「已知边界」那一节，比功能列表更能建立信任。

## 渠道 B：实战蓝皮书 Case 投稿

按「背景 → 做法 → 结果 → 可复用点」四段写，官方评审看的是**可复用性**，不是文采。

### Case 摘要（300 字，可直接提交）

```
【案例名称】访客通行：把「审批制」改成「邀请制」的开源访客系统

【背景】中小企业与园区的访客登记仍以纸质本和微信群为主，
市面产品普遍采用「访客申请—员工审批—保安盘问」的审批制，
访客体验差、责任归属模糊，且多数方案依赖云端，内网与断网场景不可用。

【做法】以「邀请」替代「审批」重构流程：员工填四个字段生成邀请卡，
微信直接转发；访客零安装；门岗单输入框核验，2 秒放行；台账自动生成。
工程上用零依赖 Node 实现，单文件 JSON 存储 + 原子写 + 每日备份，
支持断网运行。配套完成 9 张界面图、57 秒双版本演示视频、21 项冒烟测试与 CI。

【结果】开源发布（AGPL-3.0），6300 行代码，零 npm 依赖，
Node 16+ 双击即跑；GitHub Actions 在 Node 16/18/20/22 四档全部通过。

【可复用点】① 用「不做什么」定义产品边界；② 把理念写成服务端约束而非界面提示；
③ 发布物料（图/视频/文案）与代码同等投入；④ README 主动披露已知限制以建立信任。
```
