**6 字（标语）**

> 一个零依赖、可离线运行的访客邀请与门岗核验系统。

**60 字（简介）**
> 员工发一张邀请卡，微信直接转发；访客不用装 App、不用填表；门岗扫码 2 秒放行，台账自动生成。Node 16+，双击即跑，零依赖、零数据库，断网也能用。

## 二、平台文案

### 1. GitHub Release（v2.0.0）

**标题：** `v2.0.0 — 不是审批，是邀请`

```markdown
第一个开源版本。

市面上大多数访客系统默认「审批」：访客申请、员工点通过、保安盘问。
这套系统默认「邀请」：你请他来，他收到一张卡，门岗扫码放行。

它刻意做得很小：
- 零 npm 依赖，Node 16+ 双击即跑
- 零数据库，全部数据是一个 JSON 文件
- 零联网要求，断网也能发邀请、核验、查台账
- 访客零安装，邀请卡就是一张能发微信的图

功能：邀请制流程、四种卡面、一键复制图片、门岗单框核验、通行台账、
多级部门、16 项权限矩阵、操作审计、CSV 导出。

已知限制都写在 README 里，没有藏。

如果这套东西让你觉得「门口那套流程可以更体面一点」，给个 star。
```

### 2. 掘金 / 少数派（技术长文）

**标题备选：**
- 我写了一个零依赖的访客系统，然后砍掉了 90% 的需求
- 一个 JSON 文件撑起一套访客系统：零依赖、断网可用
- 为什么我把访客系统的「审批」改成了「邀请」

**开头（可直接用）：**

> 我数了一下，这套系统一共 6300 行代码，零个 npm 依赖，没有数据库，没有构建步骤。
>
> 它能做的事不少：发邀请、生成四种卡面、一键复制到微信、门岗扫码、自动台账、多级部门、16 项权限、操作审计。
>
> 但它砍掉的东西更多：门禁硬件、人脸识别、访客小程序、云端多租户、SQLite、Docker、微服务。
>
> 每砍一个，我都问自己同一个问题：加了这个，一个物业经理还能当天拍板吗？

**正文骨架：**
1. 起因：一次被盘问的经历
2. 审批制 vs 邀请制（放对照表）
3. 技术选型：为什么是「零依赖」而不是「最佳实践」
4. 三个难做的细节：原子写、核验判定顺序、门岗端只有一个输入框
5. 卡面设计：为什么一张通行证要做四种样式
6. 已知限制（诚实列出）
7. 开源协议为什么选 AGPL 而不是 MIT

### 3. V2EX（发在「分享创造」节点）

**标题：** `[开源] 写了个零依赖的访客系统，核心是「邀请」而不是「审批」`

```
公司访客登记一直用纸质本，行政嫌乱、保安嫌烦、访客嫌像审问。
索性自己写了一个。

思路和市面上的反着来：不是访客申请、员工审批，而是员工发邀请、访客接受。
邀请卡是一张 PNG，微信直接转发，访客不用装任何东西。
门岗端只有一个输入框，扫码枪和手输共用，回车就核验。

技术上有意思的地方：
- 零 npm 依赖，只用 Node 内置模块
- 数据是单个 JSON，原子写 + 每日备份，断电不会写坏
- 断网可用，适合内网/涉密场景
- 6300 行，没有构建步骤

已知短板也写在 README 里：4 位邀请码理论可猜、复入放行默认开、
没接闸机硬件、单进程。

https://github.com/ZhiGangLive/visitor-pass

想听听做过园区/写字楼项目的朋友的意见：这个方向有没有真实需求？
```

> 注意：V2EX 反感营销腔。不要写「赋能」「闭环」「数字化转型」。

### 4. 知乎（回答式）

**找这些问题回答，或自问自答：**
- 「访客管理系统哪个好用？」
- 「为什么国内的公司访客登记流程这么繁琐？」
- 「小公司有必要上访客系统吗？」

**开头：**

> 先说一个可能不太受欢迎的观点：大部分访客系统的问题，不在功能，在它默认你是贼。
>
> 你去看任何一套产品的流程——访客提交申请、员工审批、保安核验。这条链路里，
> 发起权在访客手上，判断权在保安手上，唯一该负责的人（邀请人）反而不在场。
>
> 我们把顺序倒过来了：员工发起邀请，访客接受，保安只核对凭证。

### 5. 微信公众号

**标题备选：**
- 你的公司，是在请人，还是在放人？
- 我把访客系统的「审批」删了
- 门口那三分钟，暴露了一家公司的底色

**摘要：** 一个开源访客系统的设计笔记。关于尊重，以及它在代码里长什么样。

**正文结构：**
1. 场景白描：一个客户来谈合作，在门口被问了三个问题
2. 三种人各付了一笔隐性成本（访客的尊严、保安的敌意、邀请人的时间）
3. 把动词换一下：申请→邀请
4. 理念要落在工程上（六个具体设计）
5. 邀请制不等于没有安全（判定链）
6. 克制也是尊重（不做什么）
7. 开源地址 + 一句话

## 三、60 秒视频分镜

| 时间 | 画面 | 字幕 | 旁白 / 音效 |
|---|---|---|---|
| 0–3s | 全黑，白字逐字出现 | 你邀请我来，还是叫我过来？ | 无旁白，只有低频环境音 |
| 3–8s | 纸质登记本特写，手写笔迹模糊 | 大部分访客系统，默认你在防人 | 「填表、等审批、被盘问」 |
| 8–14s | 审批流界面（可用竞品截图打码） | 访客申请 → 员工审批 → 保安盘问 | 键盘敲击声，渐弱 |
| 14–18s | 黑屏，一个字：「反了」 | 顺序反了 | 突然静音 |
| 18–25s | 发起邀请界面，快速填写四个字段 | 你邀请他，不是他申请你 | 轻快的点击声 |
| 25–31s | 卡面生成，四种样式快速切换 | 一张卡，四种样式 | 翻页声 |
| 31–37s | 复制图片 → 微信窗口 Ctrl+V → 发送 | 不用装 App，微信直接发 | 微信发送音效 |
| 37–45s | 门岗端扫码，绿色「通过」浮卡弹出 | 门岗扫码，2 秒放行 | 双高音提示 |
| 45–50s | 台账自动刷新，导出 CSV | 台账自动生成 | 表格滚动声 |
| 50–56s | 代码滚动 + `node server.js` 启动日志 | 零依赖 · 零数据库 · 断网可用 | 终端提示音 |
| 56–60s | 黑屏，金色一行字 | 不是审批，是邀请。 | 静音收尾 |

**拍摄要点：**
- 全程深色背景 + 金色高光，和界面同一套配色
- 不出现人脸，只拍手、屏幕、门口
- 前 3 秒必须出现「邀请 / 叫」这组对比，这是唯一能留住人的钩子
- 结尾不要放二维码，放仓库地址文字即可

## 五、发布节奏

不建议一天全平台铺开。按这个顺序，每步之间留 2–3 天：

1. **Day 0｜GitHub**
   补全 About、Topics、Social preview，打 `v2.0.0` tag，发 Release。
   这一步是「落地页」，其他平台的流量最终都要回到这里。

2. **Day 2｜技术社区**
   掘金 + V2EX，同一天发。技术社区看重「实现细节」和「诚实」，不要贴营销图。
   重点回复评论，前 24 小时的互动决定推荐量。

3. **Day 5｜知乎**
   找 2–3 个已有问题回答，不要自问自答（容易被判营销）。
   回答里放完整论证，链接放最后。

4. **Day 7｜公众号**
   长文，配理念。这是唯一适合放情绪的平台。
   标题用「你的公司，是在请人，还是在放人？」这类问句。

5. **Day 10｜短视频**
   B 站 + 抖音 + 小红书，同一支 60 秒，封面不同。
   小红书换成第一人称口吻，B 站保留技术细节。
